# WPGuard

Локальный сканер безопасности WordPress. Он читает файлы и, если дать доступ, базу на том сервере, где запущен. Содержимое сайта на проверку никуда не отправляется. Ключ Wordfence не нужен.

В репозитории только исходный код. Отчёты проверок, `wp-config.php` и пароли базы туда не входят и загружать их не нужно.

Проверка опирается на три открытых источника:

- контрольные суммы ядра и плагинов с `api.wordpress.org` и `downloads.wordpress.org`;
- база уязвимостей [WPVulnerability](https://www.wpvulnerability.net/) (ядро, плагины, темы, PHP, MySQL/MariaDB);
- правила и эвристика по публичным разборам заражений: отчёты Patchstack и SiteLock за 2025–2026 годы, Sucuri, разбор кампании DollyWay у GoDaddy.

По этим отчётам сайты чаще всего ломают через устаревшие плагины (около 91% новых дыр экосистемы), слабые и забытые учётки администраторов, а уже внутри оставляют PHP в `uploads`, правки ядра и плагинов, drop-in и mu-plugins, `auto_prepend_file`, скрытых администраторов и код в `wp_options` / `wp_posts`.

## Установка

Нужен Python 3.10 или новее. Склонируйте репозиторий или скачайте архив и перейдите в каталог, где лежат `pyproject.toml` и папка `wpguard`.

```bash
cd wp-guard
python -m pip install .
wp-guard version
```

На хостинге без root:

```bash
python3 -m pip install --user .
export PATH="$HOME/.local/bin:$PATH"
wp-guard version
```

Если в панели выбран другой Python, вызывайте его по полному пути. На CloudLinux это часто сборка из `/opt/alt`:

```bash
/opt/alt/python313/bin/python3.13 -m pip install --user .
```

Пакет `pymysql` ставится вместе с программой и нужен только для проверки базы.

## Запуск

Полная проверка каталога сайта:

```bash
wp-guard scan ~/public_html --php-version 8.3.16
```

`8.3.16` здесь только пример. Подставьте версию PHP из панели хостинга.

Пароль базы читается из `wp-config.php`. Если его там нет литералом, передайте доступ так:

```bash
set WP_GUARD_DB_PASSWORD=секрет
wp-guard scan ~/public_html
```

На Linux и macOS используется `export`. Аргумент `--db-password` тоже есть, но на общем сервере пароль из командной строки виден другим пользователям.

Отдельные проверки:

```bash
wp-guard malware-scan ~/public_html
wp-guard integrity-scan ~/public_html
wp-guard vuln-scan ~/public_html --php-version 8.3.16
wp-guard db-scan ~/public_html
```

Отчёт всегда записывается в файл `~/wp-guard-report.txt` в домашнем каталоге, рядом с `public_html`, а не внутри сайта. Тот же текст печатается в окне SSH. Свой путь задаётся так:

```bash
wp-guard scan ~/public_html --format json --output ~/wp-guard-report.json
```

Форматы: `text`, `json`, `csv`. Код выхода `0` — нет критичных и высоких замечаний, `2` — они есть, `1` — ошибка запуска.

Проверка в фоне, после закрытия SSH:

```bash
wp-guard scan ~/public_html --php-version ВЕРСИЯ_ИЗ_ПАНЕЛИ --workers 1 --background
wp-guard status
```

Пока проверка идёт, в `~/wp-guard-report.txt` написано, что отчёт ещё не готов. Готовый текст заменяет эту заглушку. Остановить проверку: `wp-guard stop`. Журнал хода работы: `~/.cache/wp-guard/scan.log`.

Полезные флаги:

- `--workers 2` — сколько файлов смотреть параллельно. На шаред-хостинге оставьте `1` или `2`.
- `--offline` — только локальные правила, без wordpress.org и базы уязвимостей.
- `--refresh` — заново скачать суммы и уязвимости, не беря кэш из `~/.cache/wp-guard`.
- `--min-severity high` — скрыть средние и справочные замечания.
- `--php-version` — версия PHP именно сайта. Команда `php -v` на хостинге иногда показывает другую сборку.

Повторный запуск в cron, раз в сутки:

```bash
0 3 * * * flock -n "$HOME/wp-guard.lock" "$HOME/.local/bin/wp-guard" scan "$HOME/public_html" --workers 1 --quiet --format json --output "$HOME/wp-guard-report.json"
```

## Что именно смотрит

**Файлы.** PHP, HTML, JS, `.htaccess`, `.user.ini`. Ищет запуск раскодированных строк, `assert` и команды из запроса, известные семейства шеллов, упакованные строки, PHP в `uploads` и каталоге переводов, двойные расширения, копии `wp-config`, дампы, `.env`, файлы DollyWay, drop-in и must-use плагины.

**Целостность.** Каждый файл ядра сверяется с контрольной суммой выпуска. Изменённый PHP в `wp-admin` и `wp-includes` — критичное замечание, лишний PHP в ядре — тоже. Официальные плагины сверяются с `plugin-checksums`. Плагина нет в каталоге — это справка, не тревога: платные и самописные туда не входят. У тем wordpress.org до сих пор нет официальных контрольных сумм, поэтому темы проверяются правилами и базой уязвимостей.

**Версии.** Установленная версия ядра, каждого плагина (включая выключенный: его код на диске всё ещё можно вызвать) и темы сравнивается с диапазоном уязвимости. Отдельно отмечаются устаревшие и заброшенные компоненты, закрытые в каталоге, снятые с поддержки ветки PHP и СУБД.

**База.** Только чтение. Администраторы, учётки с шестнадцатеричным именем, опции с таким же именем, PHP и `eval` в настройках, записях и cron, открытая регистрация, роль по умолчанию `administrator`, отсутствующие активные плагины.

**Настройки.** Редактор файлов в админке, показ ошибок, короткий пароль базы (сам пароль в отчёт не пишется), `xmlrpc.php`, слишком открытые права на Linux.

## Восстановление

Сначала всегда делается отчёт. Запись на диск включает только `--apply`.

```bash
wp-guard remediate ~/public_html
wp-guard remediate ~/public_html --apply
wp-guard remediate ~/public_html --apply --quarantine
```

`--apply` возвращает изменённые файлы ядра и официальных плагинов с wordpress.org. Файл записывается только если скачанная копия совпала с контрольной суммой. Предыдущая копия уходит в `~/.cache/wp-guard/backups`, не в `public_html`.

`--quarantine` переносит опасные файлы (шеллы, PHP в загрузках, копии `wp-config`, дампы) в `~/.cache/wp-guard/quarantine`. `wp-config.php` и `.htaccess` программа сама не двигает: их легко сломать и по ним сайт перестанет открываться.

Перед `--apply` сохраните свою резервную копию сайта.

## Чем это отличается от Wordfence CLI

Одинаковые задачи: малварь в файлах, известные уязвимости, база, возврат штатных файлов.

Сверка с wordpress.org для ядра и официальных плагинов здесь прямая. Подмену такого файла видно по сумме, даже если вредоносный фрагмент не похож ни на одно регулярное выражение.

Закрытой лаборатории сигнатур Wordfence у программы нет. Свежий шелл, который не похож на известные приёмы и лежит в уже изменённом самописном плагине, может не отметиться. Поэтому после критичных находок сайт стоит посмотреть глазами: чужие администраторы, недавно изменённые PHP и всё, что сканер пометил как среднее.

Программа не заменяет файрвол и не блокирует перебор пароля в момент запроса. Это проверка уже лежащих файлов и базы.
